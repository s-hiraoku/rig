# FAQ

## 一言で言うと Rig は何ですか?

ローカル CLI です。コーディングエージェントを動かして、`.rig/runs/` 以下にプレーン
ファイルとして完全な実行履歴を書き出すので、作業が検査可能なまま残ります。

## 普通に `codex exec` を呼べばいいのでは?

単発利用ならそれで十分です。直接呼ぶと失われるのは:

- 後から再実行できる安定したタスクファイル。
- 取得済みの stdout、stderr、終了コード、タイミング。
- 隔離実行から取得されるオプションのパッチ。
- 他のツール (MCP クライアント、スクリプト) が結果を読み取る標準の場所。

Rig は CLI の挙動を変えずにこの履歴を残す、最薄のレイヤです。

## エージェントアセット用のパッケージマネージャとどう違う?

Rig は意図的に、スキル、フック、プロンプトライブラリ、MCP サーバ設定を所有しません。
APM、GitHub CLI `gh skill`、Vercel `skills` のようなツールが、それらの取得・ロック・
監査・デプロイを担います。Rig は:

- エージェントコマンドを実行し、結果を保存する。
- 期待されるファイルや外部ツールが存在するかを診断する (`rig env doctor`)。
- `.rig/instructions/rig.md` に Rig 所有のポリシーを生成する。

サードパーティのエージェントアセットを勝手にインストールしたり書き換えたりは
しません。

## Rig はサンドボックスですか?

いいえ。Rig は設定済みのエージェントコマンドを、あなたのシェルで、あなたの
クレデンシャルで実行します。Worktree 実行はファイルシステム上の隔離を加えます — 
編集は `.rig/worktrees/<run-id>/` に書き出され、メインの作業ツリーは触りません — 
が、エージェントプロセス自体はローカルで動きます。

より強い隔離が必要なら、Rig 自体をコンテナや VM の中で動かしてください。

## Rig がコミットや push をしますか?

しません。Rig は `.rig/` 以下にファイルを書き、`rig worktree apply` を明示的に
呼んだときに限り、取得済みパッチに `git apply` を実行します。コミット、push、
PR の作成は一切しません。

## Codex を使う必要がありますか?

ありません。Codex がデフォルトなのは `codex exec` が安定した非対話型のプロンプト
モードを公開しているからですが、似た形の CLI なら設定できます。Claude、Gemini、
Copilot、外部 GUI エージェント (`manual` ランナー) の動作確認済みの設定は
[エージェント](agents.md) を参照してください。

## どのランナーを使うべき?

| ランナー | 使うとき |
| --- | --- |
| `exec` | CLI が単一の非対話型プロンプト引数を受け取れる。(現代的なコーディング CLI のほとんど。) |
| `manual` | 作業が GUI、チャットクライアント、Rig が起動すべきでないツールで起きる。 |
| `pty` | CLI が実 TTY を要求するため他に方法がない。実験的。 |

ほぼすべての場合 `exec` が正解です。

## `--- RIG RESULT ---` は実際に何をしますか?

stdout のマーカーです。エージェントの stdout に `--- RIG RESULT ---` リテラル行を
見つけると、Rig はそれ以降のテキストだけを `result.md` に保存します。完全な
stdout は `stdout.log` に残ります。冗長なエージェントが大量にログを書き出しても、
`rig show latest` できれいな最終回答だけが見える、という効果があります。

[実行アーティファクト → 結果抽出](artifacts.md#結果抽出) を参照。

## 実行を削除するには?

`.rig/runs/<run-id>/` のディレクトリを削除します。Rig に「削除」コマンドはありません。
実行はプレーンファイルなので、お好きなシェルツールで `.rig/runs/` を扱ってください。

## 同じタスクを複数のエージェントで動かせますか?

できます — 同じ `--task-file` を各エージェントに通します。各実行は独立した
ディレクトリなので衝突しません。
[レシピ → 同じタスクで 2 つのエージェントを比較する](recipes.md#同じタスクで-2-つのエージェントを比較する)
を参照。

## なぜ一部の MCP ツールはデフォルトで無効?

`rig_apply_patch` は作業ツリーを変更します。`RIG_MCP_ALLOW_APPLY=1` を付けて起動
しない限り無効です。デフォルトは「リモートの MCP クライアントが、明示的な人間の
オプトインなしにパッチを適用できないようにする」です。

MCP の `cwd` 値もデフォルトではサーバ起動ディレクトリ内に限定されます。
`RIG_MCP_ROOT=/path` で許可スコープを広げられます。相対パスの `task_file` は
選ばれた `cwd` 内に留まる必要があります。

[MCP サーバ → 安全デフォルト](mcp.md#安全デフォルト) を参照。

## TTY が要る CLI はどう動かしますか?

実験的な `pty` ランナーを試してください。PTY を割り当て、レンダリング済みプロンプト
を入力として書き、混合トランスクリプトを取得します。
[エージェント → 実験的: PTY ランナー](agents.md#実験的-pty-ランナー) を参照。

## `.rig/` をどのようにバージョン管理する?

多くのチームは `.rig/config.yaml` と `.rig/env.yaml` を Git に入れ、
`.rig/runs/` と `.rig/worktrees/` を `.gitignore` に追加します。実行履歴は
マシンごと、設定は共有、という整理です。

## Git なしで動きますか?

`rig init` 自体は Git を要求しませんが、Codex のデフォルトモードは要求します。
Codex 以外のエージェントの場合は、その CLI の要件次第です。Worktree 実行は
`git worktree` を使うので Git 必須です。

## Rig をアップデートするには?

```bash
uv tool install --force --refresh "rig @ git+https://github.com/s-hiraoku/rig.git"
```

Rig は `uv tool` として配布されます。専用のアップデートコマンドはありません。

## バグや機能要望はどこに送る?

[GitHub リポジトリ](https://github.com/s-hiraoku/rig/issues) で issue を作成
してください。先に `rig env doctor --json` を実行して出力を添付すると、セット
アップに関する判断材料が揃って助かります。
